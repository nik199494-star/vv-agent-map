# Пакет обновления потребности карты

## Действия менеджера

1. Загрузите свежий HRM FULL в испытательную рабочую книгу. Укажите подтверждённую рабочую дату в ячейке, настроенной для испытательного Apps Script, в формате `ГГГГ-ММ-ДД`. Дата HRM остаётся отдельной от времени принятия снимка.
2. Выберите «ВВ Preview» → «Принять снимок и создать паспорт preview». Дождитесь статуса «Паспорт preview готов» в «Автодиагностике». Сверьте дату и итоги в обеих вкладках агентской витрины.
3. Запишите UUID из `Паспорт preview!A2`, ID принятого снимка из листа «Снимки» и дату HRM из строки 3 витрины. Сохраните этот паспорт действующим до конца запуска. Срок действия — шесть часов.
4. После внедрения workflow откройте GitHub → Actions → «Подготовить пакет обновления карты» → Run workflow. Оставьте ветку `main` и внесите значения в `request_id`, `snapshot_id` и `hrm_date`. Дату вводите как `ДД.ММ.ГГГГ`. [Ручной запуск GitHub Actions](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow)
5. Когда задание `package` завершится успешно, скачайте `demand-package-…` в разделе Artifacts. В `report.md` сверьте дату, ID, число ТТ и позиций ТТ+роль, недобор и количество точек без маркера. Приложите ссылку на запуск и отчёт к запросу владельцу на выпуск. Срок хранения артефакта — 7 дней.
6. При ошибке откройте первое упавшее задание. При сбое чтения можно повторить запуск с теми же входами в пределах срока паспорта. При расхождении витрин дождитесь пересчёта или исправьте источник и создайте паспорт штатным способом. Проверка сверяет оба листа и контрольную сумму паспорта. Редактирование JSON паспорта вручную нарушает цепочку проверки.

Повторный запуск с тем же паспортом даёт одинаковые байты выпуска, пока совпадает действующий резерв. При повторной попытке GitHub сохраняет новый артефакт отдельно. Снимок, уже выпущенный, отменённый или предшествующий действующему выпуску, отклоняется. Ошибка на любом этапе останавливает загрузку артефакта.

## Подготовка доступа и испытание до merge

1. Владелец создаёт Environment `demand-package`. В правилах веток указывает только `codex/demand-package-test` на период испытания. После отдельного согласования внедрения добавляет `main` и убирает испытательную ветку из правил.
2. Владелец сохраняет в этом Environment два секрета. `VV_PREVIEW_AGENT_ID` — ID испытательной агентской витрины. `VV_PREVIEW_SHEETS_READER` — JSON-ключ действующего сервисного аккаунта с доступом «Читатель» к этой витрине. Workflow использует область `spreadsheets.readonly`. [Окружения GitHub](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments)
3. Разработчик создаёт `codex/demand-package-test` от проверенного коммита Draft PR. В отдельном коммите этой ветки добавляет `.github/demand-package-test-request.json` ровно с тремя полями `request_id`, `snapshot_id`, `hrm_date`. Это идентификаторы и дата из шага 3. Push файла запускает `package` до доступности ручного запуска в `main`.
4. Обычный PR запускает задание `fixture` с условными данными. Его артефакт помечен `TEST_ONLY`. Локальная команда `node scripts/demand-package.mjs fixture .data/package-fixture` собирает его тем же кодом. Для сохранённого чтения испытательной витрины есть локальный `replay`, тоже со статусом `TEST_ONLY`. Входной JSON содержит `request`, `points`, `cities`, `passportGrid` и хранится вне Git.

Workflow скачивает действующую карту только для проверки резерва. Environment используется с `deployment: false` для чтения секретов. Результат задания — скачиваемый артефакт Actions.

## Состав пакета и проверка перед выпуском

- `previous/` — полный действующий выпуск для восстановления. Внутри исходные байты файлов и `baseline-manifest.json`.
- `release/` — тот же набор файлов карты с новыми `demand.json`, `coordinates.json` и `publication.json`. Старые центры городов и квитанция отката остаются в составе. Координаты переиспользуются только для совпавшего адреса. Новые координаты берутся из подтверждённого геоконтроля. Точки с непроверенными адресами остаются в списке без маркера.
- `report.md` и `report.json` — результаты сверки, предупреждения и хеши. `READY_FOR_REVIEW` означает, что пакет прошёл проверки и его можно передать владельцу на согласование.

Перед рассмотрением публикации выполните `node scripts/pages-baseline.mjs verify-local <пакет>/release` и ту же команду для `<пакет>/previous`. Сверьте `previous/baseline-manifest.json` с действующей картой командой `verify`. Если карта успела измениться, соберите новый пакет. Затем проверьте diff трёх файлов и геопокрытие. Порядок выпуска и восстановления после отдельного согласования описан в [регламенте отката](rollback.md).
