# Настройка и приёмка

## Испытательная копия

1. Сохраните действующий Код.gs и ревизию привязанного проекта в закрытой папке. Зафиксируйте последний успешный выпуск GitHub Pages, значения «Снимки» и размер HISTORY.
2. Создайте закрытые копии рабочей книги и связанных витрин. Измените в испытательной версии константы VV_KNOWLEDGE и VV_AGENT и ссылки формул. Убедитесь, что цепочка IMPORTRANGE, скрытые листы v2 и Telegram используют копии.
3. Выполните команду ниже. Замените в испытательном Apps Script Код.gs содержимым Code.patched.gs. Добавьте соседние файлы Projection.gs, Diagnostics.gs, Geocontrol.gs и DemandPipeline.gs. При расхождении структуры патчер остановится.

       node scripts/patch-apps-script.mjs путь-к-Код.gs

4. Сверьте первые четыре поля справочника и расположение заголовков FULL. Для заголовков ниже первой строки задайте VV_FULL_HEADER_ROW. Для времени формирования выгрузки задайте VV_FULL_TIMESTAMP_CELL. При отсутствии этой настройки берётся максимальный updated_at с пределом в 36 часов. Проверьте это правило на реальных выгрузках.
5. Дайте менеджерам право изменения рабочей книги и чтения двух витрин. Если appsscript.json задаёт scopes явно, добавьте spreadsheets, script.external_request и script.scriptapp. Последний нужен для одноразового триггера статуса. [Разрешения Apps Script](https://developers.google.com/apps-script/concepts/scopes)

## GitHub и секреты

- Создайте отдельную служебную учётную запись Google Cloud. Включите Sheets API и выдайте ей чтение только агентской книги. JSON-ключ добавьте в секрет VV_AGENT_READER окружения github-pages.
- Создайте fine-grained PAT для одного репозитория vv-agent-map с Actions: Read and write. Установите срок действия. В Script Properties задайте VV_GITHUB_ACTIONS_TOKEN и ограничьте редакторов проекта. [Права для workflow_dispatch](https://docs.github.com/en/rest/actions/workflows?apiVersion=2026-03-10#create-a-workflow-dispatch-event)
- Оставьте VV_DEPLOY_MODE в режиме preview. Workflow проверит и соберёт данные без публикации.
- GitHub запускает workflow_dispatch после появления файла workflow в ветке по умолчанию. Рабочая ветка и PR запускают локальные тесты на сервере GitHub и собирают сайт. Облачный preview с закрытой витриной запускается после согласованного включения workflow в main. [События GitHub Actions](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#workflow_dispatch)

## Чек-лист перед выпуском

- [ ] Сверить формулы на копии. Проверить свежую и устаревшую FULL, порядок столбцов, числовой и текстовый ID.
- [ ] Сверить принятую FULL с HISTORY, «Снимки», витринами городов и точек. Повтор идентичной FULL сохраняет прежний ID. Параллельный запуск отклоняется блокировкой.
- [ ] Проверить автоправку ТТ, неопределённый город, конфликт адреса, неполное геокодирование и несовпадение недобора.
- [ ] Воспроизвести сбой Google Sheets и GitHub в испытательном режиме. Сверить содержимое публичных файлов и исключение закрытых сведений.
- [ ] После согласования сохранить текущую публикацию Pages, переключить Source на GitHub Actions и ограничить окружение веткой main. Выполнить облачный preview. [Настройка источника Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site)
- [ ] После успешного preview задать VV_DEPLOY_MODE=deploy и провести контролируемый выпуск. Проверить publication.json, дату, числа, карту, ближайшие точки, поиск метро, карточки, маршруты и мобильный вид.
- [ ] Проверить восстановление последнего корректного выпуска в согласованном окне.

Workflow публикует выпуски последовательно. Давняя дата HRM, старый снимок или устаревший запрос на тот же снимок блокируются. Если сайт после развёртывания не подтверждает выпуск, workflow пытается восстановить прежние данные и повторно проверить сайт. Артефакт прежней версии хранится 7 дней. При сбое восстановления ответственный может вернуть предыдущий артефакт или переключиться на известный рабочий коммит.
