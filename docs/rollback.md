# Первый выпуск данных и восстановление карты

Ветка добавляет проверку выпуска, оставляя прежние `demand.json`, `coordinates.json`, центры городов, интерфейс и способ публикации. Два новых файла служат исходными квитанциями. `publication.json` содержит SHA-256 трёх действующих файлов данных, а `rollback.json` пока помечен как неактивный.

## Резервная копия

1. Отдельно согласовать внедрение этих проверок. Дождаться успешного GitHub Pages deployment с этим кодом и теми же данными. Проверить карту в чистой вкладке и один раз перезагрузить вкладки, которые были открыты до внедрения. До загрузки нового кода старая вкладка не умеет применять квитанцию отката.
2. Записать SHA действующего deployment и выполнить `node scripts/pages-baseline.mjs capture .data/pages-before-release`. Скрипт дважды читает все файлы карты, сравнивает `/` с `index.html`, сверяет квитанции и SHA-256. При HTTP 503 или временном обрыве он повторяет GET целиком до трёх попыток. Для отсутствующего необязательного файла требуется HTTP 404. Готовая папка появляется только после проверки записанного архива.
3. Выполнить `node scripts/pages-baseline.mjs verify-local .data/pages-before-release` для состава и SHA-256 локальной папки, затем `node scripts/pages-baseline.mjs verify .data/pages-before-release/baseline-manifest.json` для сверки с Pages. Если ошибка сохраняется, SHA источника изменился или на Pages появились параллельные изменения, остановиться и снять новый архив. Для первого выпуска нужен архив с уже включённой поддержкой отката. Обычный архив нынешней карты сохраняет все опубликованные байты, а локальная проверка отчётливо укажет `protectedClient: false` для старого клиента.

## Публикация и проверка

1. Подготовить согласованные `demand.json` и `coordinates.json` локально. Выполнить `node scripts/pages-baseline.mjs stage .data/pages-before-release .data/approved/demand.json .data/approved/coordinates.json .data/pages-release`. Команда проверяет формат, дату HRM, новый ID и время выпуска. Она сохраняет байты входных файлов и создаёт квитанцию. Центры городов и прочие файлы берутся из архива.
2. После отдельного разрешения на выпуск перенести из пакета только изменившиеся `demand.json`, `coordinates.json` и `publication.json` одним коммитом в действующий источник Pages. Сохранить пакет и особенно точные байты выпущенного `demand.json`. Манифест хранится локально. Старые и новые файлы не должны попадать в разные коммиты. [Источник публикации GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site)
3. После успешного deployment выполнить `node scripts/pages-baseline.mjs verify .data/pages-release/baseline-manifest.json`. Проверить дату HRM, число ТТ, недобор и маркеры в чистой вкладке и в открытой вкладке кнопкой «Обновить». Пока CDN отдаёт смесь версий, карта сохраняет последний проверенный выпуск, если он уже был загружен.

## Откат

### Если не удалось впервые внедрить защиту

Этот порядок применяют до первого обновления данных. Исходный архив показывает `protectedClient: false` и содержит старый клиент. Команда `restore` предназначена для более позднего отката данных по квитанции.

1. Остановить выпуск данных и сверить SHA исходного развёртывания Pages с архивом, снятым до внедрения защиты. Распаковать ZIP в отдельную папку и выполнить `node scripts/pages-baseline.mjs verify-local <папка-архива>` из checkout с инструментами PR №5. Продолжить после успешной проверки.
2. В чистой рабочей ветке от текущего источника Pages подготовить отдельный коммит, отменяющий только первоначальное внедрение. Вернуть изменённые опубликованные файлы побайтово из архива. Удалить только новые файлы защиты, помеченные как отсутствующие (`null`) в манифесте. В исходном выпуске это `release-cache.js`, `rollback.js`, `publication.json` и `rollback.json`. Сверить diff и хеши. Если после архивирования были независимые изменения карты, согласовать состав восстановления до применения коммита.
3. После отдельного согласования владельца применить коммит существующим способом публикации Pages. Дождаться успешного развёртывания и выполнить `node scripts/pages-baseline.mjs verify <папка-архива>/baseline-manifest.json` из checkout с инструментами PR №5. Успех означает, что двоичные файлы совпали, а файлы, для которых в манифесте указан `null`, вернули HTTP 404.
4. Открыть карту в чистой вкладке, сверить дату, недобор и число точек. Во вкладках, которые успели загрузить механизм защиты, перезагрузить страницу после успешной проверки Pages, чтобы они снова использовали исходный клиент. Следующее внедрение защиты провести отдельно от выпуска данных.

### Если нужно отменить выпуск данных после внедрения защиты

1. Выполнить `node scripts/pages-baseline.mjs restore .data/pages-before-release .data/pages-release/demand.json .data/pages-restore`. Все файлы архива возвращаются с исходными байтами, включая прошлую квитанцию выпуска. Единственное новое содержимое — `rollback.json`, который указывает отменённый ID и хеши восстановленных файлов.
2. После разрешения владельца вернуть файлы из пакета одним отдельным коммитом через существующий источник Pages. Проверить diff и убедиться, что он затрагивает только файлы отменяемого выпуска и квитанцию. Если после архива появились другие изменения сайта, остановиться для сверки, чтобы их не затереть. Простое удаление квитанции или обычный revert без неё оставит тёплый кеш на более новой отменённой версии.
3. Выполнить `node scripts/pages-baseline.mjs verify .data/pages-restore/baseline-manifest.json`. В той же открытой вкладке нажать «Обновить», сверить дату и маркеры. После перезагрузки проверить кеш при сетевом сбое. Следующий выпуск после восстановления требует нового ID и времени позже отметки отката.

## Локальное испытание

`node scripts/rollback-stand.mjs 38161` обслуживает только `127.0.0.1`; команда печатает расположение файла `phase.txt`. Стенд загружает HTML и JavaScript карты, готовит архив и пакеты из условных данных. Вписывайте этапы по очереди и нажимайте «Обновить» в одной вкладке, кроме явно указанной перезагрузки.

| Этап | Что должна показать карта |
| --- | --- |
| `baseline` | Недобор 10 и 1 маркер |
| `mixed-forward` | После частичной публикации остаются 10 и 1 маркер |
| `failed` | Недобор 20, без маркера |
| `mixed` | Частичный откат отклонён, остаётся 20 |
| `restored` | В той же вкладке возвращаются 10 и 1 маркер |
| `stale` | Полностью загруженная отменённая версия отклонена по квитанции |
| `stale-without-notice` | Старая квитанция CDN не возвращает отменённый выпуск в прогретый кеш |
| `offline` | После перезагрузки при HTTP 503 остаются 10 и 1 маркер из IndexedDB |
| `forward` | Следующий согласованный выпуск загружается с недобором 30 |

Карта не регистрирует Service Worker. Для установленного кода проверенный выпуск в IndexedDB хранится под отдельным ключом от кеша старых вкладок. Квитанции защищают от рассогласованных файлов, а отметка отката сохраняется между обновлениями страницы. Чистая вкладка может получить целиком согласованный старый ответ CDN, если тот ещё не отдаёт актуальную квитанцию. Поэтому подтверждать выпуск и откат нужно только после проверки действующих публичных файлов.

При последующей совместной проверке с PR №4 сборка его интерфейса должна использовать тестовые квитанции SHA-256, рассчитанные по тем же байтам, которые отдаёт браузерная фикстура. Для Web Crypto в Chromium используйте loopback или HTTPS. Сами файлы интерфейса и логика группировки в этой ветке не меняются.
