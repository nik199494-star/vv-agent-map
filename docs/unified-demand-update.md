# Обновление из одной рабочей таблицы

## Для менеджера

1. Откройте привычную рабочую книгу, лист **HRM FULL**. Замените прежнюю выгрузку свежей FULL-выгрузкой целиком, вместе с заголовками. Перед вставкой очистите старые данные, чтобы не остались строки прежнего файла.
2. В меню **ВВ Потребность** выберите **Обновить потребность**.
3. Результат появится на листе **Обновление**. Проверка продолжается автоматически, даже если закрыть таблицу. При необходимости выберите **Проверить обновление**.
4. Только после результата **«Потребность обновлена в базе знаний и на карте. Можно сообщать агентам»** скопируйте готовый текст из строки **Сообщение агентам**.

Менеджер не меняет дату вручную, не открывает испытательные книги и GitHub. Время принятия показывается по Москве. Оно не считается датой формирования выгрузки HRM.

Если результат отличается от «Готово», сообщение агентам не отправляйте. Сохраните текст результата для технического владельца. Повторное нажатие во время обработки проверяет тот же запрос.

## Однократное подключение владельцем

Эта часть выполняется один раз техническим владельцем, а не при каждом обновлении.

- В `main` должен находиться workflow `.github/workflows/update-demand.yml`.
- Окружение `demand-package` должно разрешать `main` и содержать существующий `VV_PREVIEW_SHEETS_READER`. Этот ключ только читает Google Sheets. ID рабочей агентской витрины хранится отдельно в секрете `VV_PRODUCTION_AGENT_ID`.
- Читателю нужен доступ к рабочей **агентской витрине**, а не к внутренней HRM-книге. Подменить ID параметром запуска нельзя.
- В привязанном к рабочей книге Apps Script сохраните резерв текущего кода. Добавьте `Projection.gs` и `UnifiedDemand.gs`. В существующем `onOpen()` вызывайте `vvUnifiedOnOpen()` вместо старого меню. Остальной код нормализации и истории сохраняется.
- Удалите аннотацию `@OnlyCurrentDoc`: модулю нужно сверять две существующие внешние витрины и сохранять очищенный снимок в агентской книге. Разрешение доступа к таблицам и внешним запросам подтверждает владелец Google-аккаунта.
- В свойствах этого проекта задайте `VV_PREVIEW_DISPATCH_TOKEN`: fine-grained PAT только для `vv-agent-map`, права **Actions: write** (и обязательное Metadata: read). Права Contents: write и доступ к HRM для этого PAT не нужны. Токен вводит владелец; его нельзя помещать в ячейки, код, логи или репозиторий.
- В тех же свойствах один раз задайте `VV_WORK_BOOK_ID`, `VV_KNOWLEDGE_BOOK_ID`, `VV_AGENT_BOOK_ID` — идентификаторы существующих рабочей книги, базы знаний и агентской витрины. Их значения не публикуются в коде.
- Выполните `vvInstallUnifiedUpdate`. Он проверяет наличие workflow и создаёт лист результата. Публикацию установщик не запускает.
- Запустите полное обновление на реальной свежей выгрузке, проверьте обе витрины, фактически опубликованные 24 файла, экран мобильного агента и состояние ранее открытой вкладки. До этого подключение нельзя считать проверенным в работе.

## Что делает обновление

Команда проверяет FULL и штатный Контроль, вызывает прежнее принятие RAW с историей, затем сравнивает точки, роли, недобор, города и общие условия в рабочей книге, базе знаний и агентской витрине. Формулы действующих витрин сохраняются.

Три скрытых технических листа **Публикация точки**, **Публикация города**, **Паспорт публикации** создаются автоматически внутри существующей агентской книги. Это зафиксированная очищенная проекция одного запроса. HRM FULL, внутренние контакты и учётные данные туда не копируются. Скрытие листа не считается защитой доступа: в них разрешены только уже публичные поля витрины.

В Actions передаётся только UUID запроса. Workflow читает зафиксированные данные, проверяет паспорт и согласованность, сохраняет проверенный предыдущий выпуск и собирает новый. Изменившийся адрес лишается старого маркера до ручного подтверждения координат.

Обычный ежедневный коммит может менять только `demand.json`, `coordinates.json`, `publication.json`. Изменения `main` и расхождения с действующей картой останавливают автозамену. Принудительная перезапись ветки запрещена. После коммита выполняется явный запрос сборки существующего GitHub Pages; менять источник публикации Pages не требуется.

Успех workflow требует совпадения всех 24 фактически публичных файлов с пакетом. Таблица дополнительно проверяет точный запуск, шаг сверки, ID снимка на карте и отсутствие новых правок входных данных. До этих проверок готового сообщения агентам нет.

При неопределённом ответе на отправку скрипт ищет существующий запуск по UUID и не повторяет POST. При повторном ручном запуске workflow уже созданный коммит используется повторно. Если выпуск не подтверждён, архив и технический результат сохраняются в артефакте Actions на 30 дней; предыдущий выпуск также остаётся в истории git. Автоматическое восстановление без проверки владельцем не выполняется.
